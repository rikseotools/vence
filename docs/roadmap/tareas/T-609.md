  `cerrar.ts` **no manda por BD**, manda por HTTP contra `/api/v2/dispute/resolve` con el token de
  admin, así que una sesión con la BD caída —o sin `.env.local`, que es la condición NORMAL de un
  worktree [T-539]— habría enviado el correo vetado igual. El agujero que esta ficha vino a tapar
  seguía abierto por debajo.
  **Arreglado:** `sin_bd` ahora BLOQUEA. Mismo criterio que [T-615] de esta misma jornada
  (§6.ter.bis de `sistema-sesiones-paralelas.md`): *fail-open es para la OPERACIÓN, nunca para el
  VEREDICTO* — esta puerta no observa, decide si sale un correo hacia una persona. Y lo respalda la
  asimetría que ya razonaba `embudoVeto.cjs`: un falso «sí» manda un correo vetado (irreversible);
  un falso «no» cuesta un `--embudo-igualmente` con motivo, que ya existe. Se conserva el
  razonamiento del test original: cuenta como `guard_bloqueo` y **no** como `guard_escape` —contarlo
  como escape inflaría el indicador de «guardarraíl que se rodea» cada vez que se cae la BD— y el
  mensaje dice **cómo** satisfacerlo (`--env-file=.env.local`), que es lo que evita que un bloqueo
  acabe enseñando a usar el escape ([T-375]).
